### **Project Summary: Unified Chat Archive Conversion Framework**

**High-Level Goal:**
The primary objective of this project is to create a versatile and scalable Python framework capable of parsing chat logs from multiple messaging services, unifying them into a standardized format within a central database, and generating rich, interactive HTML archives from this data. The framework is designed to handle the unique export formats and complexities of each service, ultimately producing a consistent, user-friendly output.

---

### **Phase 1: Foundational Requirements & WhatsApp Implementation**

*   **Initial Service:** Support for parsing exported WhatsApp chat logs from a `.txt` file.
*   **Core Parsing Logic:**
    *   Utilize regular expressions to identify and parse individual message lines, distinguishing them from multi-line continuations.
    *   Extract key metadata: timestamp, author, and message body.
*   **Media Handling:**
    *   Identify messages indicating an "image omitted" and process the corresponding local image files.
    *   Copy attachments to a structured output directory.
    *   Rename media files based on their message timestamp to ensure chronological sorting and prevent filename collisions.
    *   Utilize `ExifTool` to embed the correct creation date metadata into image files.
*   **Content Enrichment:**
    *   Integrate with the OpenRouter AI API to provide optional, on-the-fly translation of non-English messages.

---

### **Phase 2: Expansion to Multiple Services & Initial Refactoring**

*   **New Service:** Add support for Facebook Messenger chat logs from a `.json` file.
*   **Structural Refactoring:**
    *   Transition from a single-purpose script to a multi-service tool.
    *   Implement an interactive command-line menu for service selection (WhatsApp, Messenger).
    *   Replace hardcoded file paths with dynamic user prompts.
*   **Messenger-Specific Parsing Challenges & Solutions:**
    *   **Reverse Chronological Order:** Process the JSON message array in reverse to maintain chronological accuracy.
    *   **Timestamp Conversion:** Convert epoch timestamps (in milliseconds) to standard `datetime` objects.
    *   **Unicode & Encoding:** Address and fix `mojibake` text corruption by correctly re-encoding strings that were exported as UTF-8 but misinterpreted as `latin-1`.
    *   **Attachment URI Parsing:** Implement logic to parse the `uri` field for photos and videos, constructing the correct relative path to the local attachment files.
    *   **Intelligent Translation Skipping:** To avoid redundant API calls, implement a system to detect and skip the translation of messages that appear to be user-provided translations. The logic identifies consecutive messages from the same author, within a short time window (~5 minutes), that have a similar character count (within a 20% tolerance) but are in different languages.
    *   **Shared Link Handling:** Parse and preserve `share` objects, embedding the shared link and its preview text into the message body.

### **Phase 3: The iMessage Processing Pipeline (Advanced Use Case)**

This phase represented a significant increase in complexity, requiring a multi-step, intermediate-file-based workflow to handle the non-standard output of the `imessage-exporter` tool.

*   **Source Format:** A directory containing multiple HTML files (named by contact phone/email) and a deeply nested `attachments` folder.
*   **Intermediate Goal:** Convert the unstructured HTML export into clean, per-author JSON files.
*   **Workflow Implementation:**
    1.  **File Pre-processing:**
        *   **Author Identification:** A function was developed to intelligently parse filenames, separating the author's name from appended phone numbers or emails. This logic was refined to handle edge cases like extra whitespace and trailing commas.
        *   **File Organization:** The script renames the HTML files to encapsulate the detected author name in brackets (e.g., `[John Doe]...html`) and then organizes these files into author-specific subdirectories.
    2.  **HTML-to-JSON Conversion:**
        *   **Parallel Processing:** Implemented `concurrent.futures` to process each author's folder in parallel, significantly speeding up the conversion of large archives. A `tqdm` progress bar was added for user feedback.
        *   **Robust HTML Parsing (`BeautifulSoup`):**
            *   Handles complex and inconsistent HTML structures, including messages with **multiple attachments**, attachments nested inside `sticker` divs, and attachments outside of standard `message_part` wrappers.
            *   Extracts timestamps, sender information, message bodies, and shared link/app data.
            *   Parses **tapbacks** (reactions), maps the text (e.g., "Liked") to a corresponding emoji ("👍"), and associates it with the correct message.
        *   **Advanced Attachment Handling:**
            *   Recognizes a wide variety of attachment tags (`<img>`, `<video>`, `<audio>`, `<a>`).
            *   **Moves** (not copies) attachments from the central `attachments` folder to categorized subfolders (`images`, `videos`, `data`) within their respective author's directory.
            *   For non-media files (e.g., PDFs, VCFs), it restores the original filename by parsing it from the link's anchor text.
    3.  **The Pivot to a Database Backend:**
        *   It was determined that creating a single "master" JSON file was inefficient and unscalable for the "All Chat" view.
        *   **Decision:** Use a **SQLite database** as the canonical data store.
        *   **Schema Refinement:** The database schema was carefully designed to be unambiguous. After identifying confusion with terms like "author" and "sender," the final schema was defined with `message_owner` (the archive owner), `message_author` (the conversation partner or group), and `message_sender` (the individual who sent a specific message). This model robustly handles both one-on-one and group chats.
        *   An `attachment_author_dir` column was added to store the parent directory of each attachment, enabling the construction of correct relative paths for both individual and "All Chat" HTML views.
    4.  **Data Enrichment During Database Ingestion:**
        *   The user is prompted for their `message_owner` name at the start of the database creation process.
        *   The script optionally accepts a Vcard (`.vcf`) file to build a reverse-lookup table (phone/email -> contact name).
        *   During database insertion, the script uses this lookup to clean the `message_sender` field, replacing raw phone numbers/emails with proper names and storing the full contact info for a future tooltip feature.

### **Phase 4: Final Architectural Refactoring (OOP Framework)**

The final phase was to refactor the monolithic script into a professional, object-oriented framework to enhance scalability, maintainability, and prepare for a potential future port to Swift.

*   **Core Principle:** Separation of Concerns.
*   **New Architecture:**
    *   **`main.py` (The Conductor):** Stripped of all business logic. Its sole responsibility is to manage the user interface and orchestrate the interaction between the other components.
    *   **`src/database_manager.py`:** A `DatabaseManager` class that encapsulates all SQLite operations (creation, insertion, querying).
    *   **`src/html_generator.py`:** An `HTMLGenerator` class that handles all Jinja2 template rendering.
    *   **`src/parsers/` (The Engine Room):**
        *   `base_parser.py`: An Abstract Base Class defining a common interface (`parse()` method) that all parsers must implement. This is the key to the unified framework.
        *   Concrete parser classes (`WhatsAppParser`, `MessengerParser`, `IMessageParser`) inherit from `BaseParser` and contain the service-specific logic.

*   **Security:** The hardcoded OpenRouter API key was moved to an external `API_Key.env` file, which is ignored by Git via a `.gitignore` file, using the `python-dotenv` library for secure loading.
