# Phase 1.5 - PDF Requirements

## Overview

PDFs come into the box in three stages. Only the first is required:

```
 original PDFs (file, folder, zip)                    the box
   never moved or changed ──IMPORT──► inspect ─► OCR pages that need it ─► validate ─► Documents/PDF/<YYYY>/<Author>/
                                        │                                    │           (date) Title - Author.pdf
                                        │                     failed? ──► archive the unchanged copy, To review
                                        ▼
                               page text ─► full-text index
                                        │
                           ──ENRICH──► filename + properties + text ─► local model ─► reconcile
                                        │  confident: rename / move     not: To review
                                        ▼
                           ──FIND──► Documents ▸ PDF view, YYYY/Author card pages, overlay,
                                     search, Ask (with page citations), person pages
```

1. **Import** (the `pdf` collector). Caixa finds every PDF in a file, folder (recursive) or zip,
   and skips the ones it already has (by SHA-256). It works on a copy. It inspects each page and
   OCRs only the pages that need it. Every processed PDF is validated before it is accepted. The
   archived copy goes to `Documents/PDF/` with its page text in the master. Preview, progress,
   cancel, undo and run-again come from the collector contract.
2. **Enrich** (optional; a job stage after an import, or a command). A model on this computer reads
   the filename, the PDF's properties and the opening and closing pages. It proposes the type,
   title, author, dates, tags, people and a summary, each fact with its evidence. Caixa checks that
   evidence and reconciles it with the filename. Confident results rename and refile the document;
   anything else goes to **To review**.
3. **Find.** The index page gains **Documents ▸ PDF**: a heat map of document dates, a year range,
   years and authors as tiles, Unrecognized and To review. Each year-and-author page shows cards in
   date order, and each card opens the PDF in an overlay. With Caixa running there is also
   full-text and semantic search, **Ask** (answers that cite document and page), correction tools,
   and documents on the pages of the people they involve.

The draft specification's seven phases map onto this project as phases 1–6; phase 7 (financial
transactions) stays in the backlog.

## Goals

- Import PDFs from files, folders (recursive) and zips. Never move, change or delete a source.
  Importing again adds only what is new.
- Give every archived PDF a searchable text layer wherever text is visibly present. OCR only the
  pages that need it; never rasterize a digital page.
- Validate every processed PDF (structure, content, appearance) before accepting it; never lose a
  document to a failed step.
- Work out type, title, date, author, tags, people and a summary with a local model. Treat the
  filename as evidence, record where every fact came from, and flag conflicts.
- Establish Caixa's archival naming convention as a documented, reusable deliverable.
- Find documents by words (by page), facts (filters) and meaning (semantic search, Ask with
  citations).
- Browse documents in the box with or without Caixa running; correct them when it is running.
- Link documents to the people of the box.

## Non-goals

- A standalone document-management application; an accounting system.
- Converting PDFs to HTML, or drawing them with a viewer of Caixa's own (no pdf.js): the browser's
  own viewer shows them.
- Changing, moving or deleting original files; removing a PDF's encryption.
- Sending document contents to any service on the internet: documents go only to a model on this
  computer, even when summaries or translation allow a remote service.
- Transaction-level financial extraction, linking cheques to bills, spending histories (draft phase
  7: backlog).
- Other formats (Word, spreadsheets, presentations, text): the domain and folder layout leave room
  for them; each will get its own collector.
- Requiring a model or OCR for an import to succeed.
- Merging two different files that hold the same document (they are flagged, not merged).

## Architecture

### Components

| --- | --- | --- |
| **PDF collector** | `caixa/collectors/pdfImport.py`, entry point `pdf = "caixa.collectors.pdfImport:collectors"` | `CollectorInfo` id `pdf`, name "PDF documents", inputs `file`, `folder`, `zip`; a "how to collect" card. `preview` counts PDFs, those already in the box, duplicates within the source, encrypted and unreadable ones, pages likely to need OCR, total size. `run` drives the pipeline below per PDF in up to the Workers setting processes, reports progress by stage, and returns `RunResult` with `moved` for undo. Named for its format: each later format gets its own collector over the shared domain code. |
| **Document domain** | `caixa/documents/` | Format-neutral code: records, naming, reconciliation, enrichment, pages, search. Each format plugs in its own reading, inspection and normalization. |

Flags encryption and damage. Thresholds are set on the fixtures and the first real folder. |
| **OCR** | `caixa/documents/pdf/ocr.py` | OCRmyPDF's Python API on the working copy, only for the pages that need it (`pages=`), with `skip_text` for pages that have text and `redo_ocr` where an existing OCR layer is unusable. Asks for a JSON object of the classification schema, then, for the eight types with their own fields, a second object of that type's schema. Validates each answer against its schema (one retry, then To review). Verifies every evidence quote against the text of the page it cites. Records model, provider, prompt version, schema version and time. |
| **Reconciliation** | `caixa/documents/reconcile.py` | Caixa's own rules, not the model's: each field's candidates from the filename, the properties, the text and the model are merged when they agree (the sources listed), recorded as a conflict when they disagree, and a filename value is kept unless evidence contradicts it. Decides confidence (see *Confidence and review*) and applies or sends to review. |

### The box

```
Documents/
  PDF/
    2024/
      Banco Atlântico/
        Banco Atlântico 2024.html                         the year-and-author page of cards
        (2024-11-30) Checking Statement - Banco Atlântico.pdf
        (2024-10-31) Checking Statement - Banco Atlântico.pdf
      Unrecognized/
        Unrecognized 2024.html
        (2024-03) scan_00482.pdf                          not yet attributed
    Undated/
      Unrecognized/
        Document1.pdf
```

- **Folders**: `Documents/<FORMAT>/<YYYY>/<Author>/` (decided 2026-11-24). The format folder
  (`PDF`, later `DOCX`, …) keeps formats apart. Category and type are not folders: they are facts,
  shown as views and filters, so reclassifying never moves a file. The year is the naming date's.
- **Unrecognized** (the word the index page already uses): documents without an author yet. The
  owner can type the author on a card; the file then moves to that author's folder.
- **Undated** (NEEDS MAINTAINER CONFIRMATION): documents with no date at all.
- The `Documents/` folder is made when the first document arrives; the box README gains a line
  for it.
- The page file name `<Author> <YYYY>.html` is NEEDS MAINTAINER CONFIRMATION.

### Naming convention

A deliverable of this project, documented for every file collector (the document's name and place
are NEEDS MAINTAINER CONFIRMATION; proposed `docs/Archival names.md`). It extends what Caixa
already does (`(YYYY-MM-DD) name` for attachments, conversation pages, Cleaned and Reduced mboxes;
` (2)` on a clash).

```
(DATE) Title - Author.ext
```

- **Date**: the naming date at its precision: `(2024-11-30)`, `(2024-11)`, `(2024)`. A full date is
  never invented from a partial one. With no date, there is no prefix (NEEDS MAINTAINER
  CONFIRMATION).
- **Which date names a document** (proposed, by type):

  | Type | Naming date |
  | --- | --- |
  | Statement | end of the period |
  | Bill, invoice, receipt | issue date |
  | Cheque | date written |
  | Tax document | tax year, at year precision |
  | Insurance | start of the coverage period |
  | Legal agreement | execution date |
  | Correspondence | date of the letter |
  | Other | the document's own date, else the issue date |

  Every other date (issue, creation, effective, due, period, tax year, download) is kept as its own
  field and never conflated. The file's modification or download date is recorded and never names
  a document.
- **Title**: what the document is, short ("Checking Statement", "Property Tax Bill", "Cheque 1042 to
  Canalizações Rui"), in the document's language. Words in capitals become title case. It does not
  repeat the date or the author.
- **Author**: the issuer, sender or creator (not the subject or the recipient), by the author's
  canonical name. Omitted when unknown. Kept in the name even though it is also the folder, so a
  file copied out of the box still says what it is (decided 2026-11-24).
- **No tags** in file names (decided 2026-11-24): they change on re-enrichment, and each change
  would rename the file.
- **Before enrichment** a document keeps its original name after the date: `(2024-03) scan_00482.pdf`.
- **Characters**: NFC; `/ \ : * ? " < > |`, control characters and leading or trailing dots and
  spaces replaced or removed; runs of spaces collapsed; the extension lower case.
- **Length**: at most 120 characters with the extension; a long title is cut at a word.
- **Clashes**: a different file with the same name in the same folder gets ` (2)`, ` (3)` before
  the extension.

### Pipeline, statuses and failure

Per PDF, in a worker process:

1. **Identify.** SHA-256 of the source. Known already: a `document_sources` row is added (another
   place the same file was seen) and nothing else is done. A file that cannot be read is reported
   with its path and left where it is.
2. **Copy** to `.caixa/work/documents/<job>/` (the owner-only working folder); the source is never
   opened for writing.
3. **Inspect** each page (see *Components*).
4. **OCR** the pages that need it, if OCRmyPDF and Tesseract are present. If they are missing, those
   pages are `needs_ocr` and the document is archived as it is.
5. **Validate** the output. If it fails, the **unchanged copy** is archived instead. Its hash equals
   the source's, so it is valid by definition. The document is marked `ocr: failed` and goes to To
   review; the failed output and its report stay in `.caixa/work/documents/failed/<id>/`; and
   `caixa documents reprocess` retries it, also with other settings.
6. **Archive** into the box (see *Naming convention*), with the year from the filename, the text or
   the properties, in that order, and the author when it is already known from an alias in the
   filename or the properties. Otherwise the document goes to `Unrecognized/`.
7. **Store** each page's text (from the PDF or from OCR), the facts and the run, and index the text.
8. **Enrich** after the import, if on (see below).

Statuses kept on each document:

- `processing`: `archived` | `needs_review` | `failed`
- `ocr`: `not_needed` | `done` | `partial` | `needs_ocr` | `failed`
- `validation`: `passed` | `unchanged_copy` | `failed`
- `ai` (from the draft): `pending` | `processing` | `completed` | `needs_review` | `failed`
- `review`: the reasons a document is in To review (conflict, low confidence, unknown author, OCR
  failed, locked, probable duplicate)

**Encrypted PDFs** that need a password are archived byte for byte, without text, and listed in
To review as locked. The browser's viewer asks for the password. Caixa never removes encryption.

**Probable duplicates.** A different file whose normalized text has the same hash as a document
already in the box (a statement downloaded twice) is imported and flagged as probably the same as
the other, never merged.

### Enrichment, confidence and review

- **Provider**: the box's summaries setting (Automatic: Apple Intelligence first, else the
  OpenAI-compatible endpoint, e.g. LM Studio). A non-local endpoint is refused for documents
  whatever `summaries.allow_remote` says.
- **Structured output**: endpoints get `response_format` with the JSON schema (LM Studio supports
  it). The Apple helper gains guided generation from a schema where Foundation Models allow it,
  otherwise the schema goes in the instructions. Caixa validates every answer itself either way.
- **Classification schema** (version 1):
  - `category` and `type`, from fixed vocabularies:
    - Financial: statement, cheque, bill, invoice or receipt, insurance, tax;
    - Legal: agreement, property record;
    - Personal: medical, personal record;
    - Correspondence;
    - Business;
    - Other;
  - `title`;
  - `author` {name, evidence, page};
  - `date` {value, precision, kind, evidence, page};
  - `other_dates[]`;
  - `people[]`, `organizations[]`, `properties[]`;
  - `tags[]` (at most four, from the vocabulary);
  - `summary`;
  - `filename_conflicts[]`.
- **Type schemas** (version 1), each field with evidence and page:

  | Type | Fields |
  | --- | --- |
  | Statement | institution, account type, account suffix, period, opening and closing balance |
  | Cheque | number, date, payee, amount |
  | Bill | provider, service address, billing period, amount due, due date |
  | Invoice or receipt | vendor, number, date, total |
  | Insurance | insurer, policy number, coverage period |
  | Tax | issuer, tax year, form |
  | Legal agreement | parties, subject, execution date |
  | Correspondence | sender, recipient, date, subject |

  Amounts are stored as the text found and as a number parsed by Caixa (never computed by the
  model).
- **Evidence check**: a quote must be found, after normalizing spaces and case, in the text of the
  page it cites. A field without verified evidence stays a proposal.
- **Confident** means all of the following:
  - type, title and date are present with verified evidence;
  - the author is a known author, or its name is found in the text;
  - nothing contradicts the filename's evidence;
  - the answers passed their schemas.

  A confident document is applied: its fields are set, then it is renamed and moved (recorded for
  undo) and its pages are redrawn. Anything else is applied only as far as it is safe (the summary
  and tags), and the document goes to **To review** with its reasons.
- **Corrections** by the owner (author, title, date and precision, type, tags) are marked
  `user_verified`. Enriching again never overwrites them. Each correction renames or moves the file
  and joins the batched **Update the pages**.
- **Re-enrichment** (a new prompt or schema version, another model) replaces the proposals of the
  earlier run in place: no duplicate records, and the history keeps both runs.

### Data model

**The master database**, migration 6:

- `items`: one row per document. Id `pdf:<source SHA-256>`; type `document`; collector `pdf`;
  `timestamp_utc` the naming date (midnight UTC) with `time_precision` `day`, `month` or `year`;
  `text` the summary (page text lives in `document_pages`); `file_path` the archived path relative
  to the box; `content_hash` the archived SHA-256.
- `documents`:
  - `item_id`, `format`, `original_filename`;
  - `source_sha256` (unique), `archived_sha256`, `size`, `pages`;
  - `title`, `author_id`, `category`, `type`;
  - `date`, `date_precision`, `date_kind`;
  - `summary`, `summary_model`;
  - `processing_status`, `ocr_status`, `validation_status`, `ai_status`, `review` (reasons, JSON);
  - `text_hash`, `created_at`, `updated_at`.
- `document_sources`: item, path where it was found, filename, size, modification time, first seen,
  import id.
- `document_pages`: item, page number, text, `source` (`pdf` | `ocr`), quality and class.
- `documents_fts`: FTS5 over `document_pages.text` (external content), `unicode61 remove_diacritics
  2`.
- `document_fields`: item, field, value, value as number (amounts), source (`original_filename` |
  `pdf_metadata` | `pdf_content` | `ocr` | `ai_inference` | `user_verified`), evidence, page,
  state (`proposed` | `applied` | `conflict` | `rejected`), run id. Several rows per field, one per
  supporting source.
- `document_tags`: item, tag. `tags`: the vocabulary, extendable by the owner.
- `authors`: id, name (unique), kind, person id. `author_aliases`: author, alias, normalized.
- `document_runs`: item, stage (`ocr` | `validate` | `enrich` | `reprocess`), tool and version,
  settings, model and provider, prompt and schema version, result, report, time.
- Phase 6: `chunks` (item, page, start, end, text, embedding as float32, embedding model): keyed by
  `item_id` so Stage 2 can add mail and messages. Author and people links in `item_people`
  (`sender` for the author, `recipient` for whom it is addressed to, `mentioned`). The owner is not
  linked as recipient, since nearly every document is addressed to them.

**Working files**: `.caixa/work/documents/`, readable only by the owner: job working copies
(removed when the job ends), `failed/<id>/` with output and report, OCR logs. Nothing there is
needed to read the box.

**Box settings**: `documents.enrich` (on), `documents.ocr` (on), `documents.ocr_languages`
(proposed `eng+por`), `documents.embedding_model` (empty: none).

### Search and Ask

- **Full text**:
  - Words, "exact phrases", prefixes. Numbers like `450.00` and `4821` are matched as the index
    splits them.
  - Results are ranked by BM25. Each shows the document, the page and a snippet; opening one goes
    to that page in the overlay.
  - Filters: type, category, author, date range, tags, status, person.
  - Available through `documents.search` and `caixa documents search`.
- **Served**: the Documents view has a search box and filters when the page is opened through
  `caixa serve` (the box's pages may already call the service).
- **From disk**: the same view filters its cards by their own words (title, author, type, tags,
  summary), without full text.
- **Semantic (phase 6)**:
  - Each page is split into passages of about 1,000 characters with overlap.
  - Embeddings come from the endpoint's `/v1/embeddings` with the embedding model setting, or from
    Apple's `NLContextualEmbedding` through the Swift helper, compared on the Mac.
  - Cosine similarity is computed with numpy, and combined with full text by reciprocal rank
    fusion.
  - Embedding is a resumable stage, like summaries.
- **Ask (phase 6)**:
  - A question retrieves the best passages: about four for Apple Intelligence, eight for an
    endpoint.
  - The model answers only from them, citing `[n]`.
  - Caixa maps each citation to its document and page and refuses an answer whose citations do not
    match. The answer is shown with the cited passages, each opening the PDF at its page.
  - The answer is marked as written by a model.

### Key flows

- **Import**:
  1. Wizard: PDF documents → choose a file, folder or zip → preview (found, already in the box,
     duplicates, encrypted, unreadable, likely OCR pages, size) → start.
  2. Job: workers identify, copy, inspect, OCR, validate and archive; one writer stores to the
     master and the index.
  3. Pages are drawn, then the enrich stage runs (if on), then the report.
- **Enrich**: for each document with `ai` `pending`, or one whose prompt or schema version
  changed: build the input → classify → type fields → check the evidence → reconcile → apply or
  review → summary and tags → redraw. It can be stopped and continued.
- **Review**: the To review list (served) shows each document's reasons, its candidates side by
  side with their sources, and its card. The owner chooses or types the values; the document is
  applied and redrawn.
- **Undo**: the newest import is undone like any import. The snapshot holds the master, new files
  are removed, and moves are reversed.

### Workers

- Per PDF: identify, inspect, OCR and validate run in up to the Workers setting processes. OCRmyPDF
  runs with one job per PDF while several PDFs are processed at once.
- Storing to the master and the index is done by one writer.
- Enrichment runs as many requests at once as the provider takes, as for summaries.

## Requirements

- **D1 Collector.** A `pdf` collector in `caixa/collectors/pdfImport.py`, registered by entry
  point, takes files, folders (recursive) and zips, and offers preview, progress, cancel, undo and
  run-again, with its card in the import wizard.
- **D2 Originals untouched.** Sources are opened read-only. Their bytes and modification times are
  unchanged by any step; nothing is moved or deleted.
- **D3 Identity.** A document is identified by its source SHA-256. Importing it again, from any
  path, adds a source row and nothing else. Re-runs are idempotent.
- **D4 Inspection.** Every page is classified as text, needs OCR, existing OCR layer, broken text or
  blank, and encrypted and damaged files are recognised.
- **D5 OCR.** Only pages that need it are OCR'd, with OCRmyPDF (`pages`, `skip_text`, `redo_ocr`,
  `output_type pdf`, `optimize 0`). Digital pages are never rasterized. Broken-text pages keep
  their look, and their OCR text is stored. A PDF needing no OCR is archived byte for byte.
- **D6 Validation.** Every processed PDF passes the structural, content and appearance checks before
  it is accepted. On failure the unchanged copy is archived, the document goes to To review, the
  failed output is kept, and it can be reprocessed.
- **D7 Hashes and history.** Source and archived SHA-256 are recorded, and each run's tool,
  version, settings and result.
- **D8 Placement and names.** Files are placed and named by *The box* and *Naming convention*, and
  every path in the master is relative to the box.
- **D9 Naming convention.** The convention is documented for reuse and implemented in
  `caixa/naming.py`, with the examples and edge cases of this file as tests.
- **D10 Page text and index.** Each page's text (PDF or OCR) is stored and indexed in FTS5.
- **D11 Evidence.** The filename and PDF properties are read deterministically. Uninformative
  filenames are recognised as such, and the original filename stays on the record.
- **D12 Enrichment.** A local model proposes the classification and type fields as JSON of
  versioned schemas, each fact with evidence and page. Answers are validated and evidence is
  verified. Model, prompt version, schema version and time are recorded. A non-local endpoint is
  refused.
- **D13 Reconciliation and provenance.** Field candidates from every source are kept with their
  sources. Agreement merges them, disagreement is recorded as a conflict, and filename information
  is kept unless contradicted. Date kinds are never conflated.
- **D14 Confidence, apply, review.** Confident proposals are applied (rename and move, recorded for
  undo); the rest go to To review with reasons.
- **D15 Authors.** Authors with aliases and kind, which the owner can rename and merge, with
  folders following. An author can be linked to a person of the box.
- **D16 Summary and tags.** A 30–50-word summary in the document's language, marked as a model's,
  and at most four tags from the vocabulary.
- **D17 Optional AI.** Import succeeds with no model and no OCR tools. Enrichment can run later and
  again (`caixa documents enrich`).
- **D18 Benchmark.** `caixa benchmark` gains a documents task, timed and scored against the
  fixtures' known answers, for Apple Intelligence and an endpoint.
- **D19 Serving and overlay.** PDFs are served inline. A card's **Open** shows the PDF in an overlay
  drawn by the browser's viewer, with page jumps, from `caixa serve` and from disk.
- **D20 Pages.** Documents ▸ PDF on the index page: a heat map with a year range, years and author
  tiles, Unrecognized and To review. Each year-and-author page shows cards in date order with:
  - the archival file name, title, date (at its precision), author, type and category;
  - tags, the original filename, a summary marked as a model's;
  - processing and validation status;
  - **Open**.
- **D21 Search.** Full text with page and snippet, filters on facts, through the service, the
  command line and the served Documents view. The view also filters its cards when opened from
  disk.
- **D22 Correction.** When served: the author can be set for Unrecognized documents; author, title,
  date, type and tags can be corrected (`user_verified`, never overwritten); redraws are batched.
- **D23 Semantic search.** Passages and embeddings (endpoint or Apple), hybrid ranking with full
  text, resumable.
- **D24 Ask.** Questions answered by the local model from retrieved passages, with checked citations
  to document and page, marked as a model's.
- **D25 People.** Authors and people named are matched to the box's people and recorded in
  `item_people`; their pages list those documents with **Open**.
- **D26 Privacy.** No page text or extracted value goes into a log; working files are
  owner-readable only; AI-written facts are always distinguishable from verified ones.
- **D27 Doctor and licence.** `caixa doctor` reports the PDF and OCR tools. NOTICE and README state
  PyMuPDF's AGPL-3.0 terms and the tools to install.

## Acceptance criteria

- [ ] Importing the synthetic PDF folder (recursive) and its zip leaves every source's bytes and
      modification time unchanged; importing it again adds no record; the same file at two paths
      is one document with two sources.
- [ ] Archived PDFs are under `Documents/PDF/<YYYY>/<Author>/`, named by the convention, with
      `(2024-11)` and `(2024)` for partial dates and ` (2)` on a clash; every master path is
      relative to the box.
- [ ] A digital PDF is archived byte for byte (archived hash = source hash); a scanned PDF gets a
      text layer on every page; a mixed PDF is OCR'd only on its scanned pages; an existing good OCR
      layer is kept; a broken-text page looks the same and is found by its OCR text.
- [ ] Every archived PDF passes validation. A forced OCR failure archives the unchanged copy, keeps
      the failed output, marks the document for review, and `caixa documents reprocess` succeeds
      once the cause is removed.
- [ ] Page count, order, sizes and appearance of every processed fixture match the source within
      the tolerance.
- [ ] With OCRmyPDF absent, the import succeeds, scanned pages are `needs_ocr`, and `caixa doctor`
      says what to install.
- [ ] Encrypted, corrupted and duplicate fixtures are handled as specified (locked in To review;
      reported and left alone; flagged as probably the same).
- [ ] With the stand-in model, the fixtures with descriptive filenames are applied with the right
      type, title, author and date. A misleading filename produces a recorded conflict and To
      review. An uninformative filename gets its facts from the text. No filename fact is dropped
      without contradicting evidence.
- [ ] Every applied field has verified evidence and its sources. Date kinds (statement period,
      issue, tax year, effective) stay separate. Amounts are parsed by Caixa.
- [ ] Without a model the import succeeds and the documents are under Unrecognized with their
      original names after the date; enriching later renames and moves them, and undo puts them
      back.
- [ ] Re-enriching with a new prompt version creates no duplicate record and keeps
      `user_verified` fields.
- [ ] A non-local endpoint is refused for documents even with `summaries.allow_remote` on.
- [ ] Searching a word printed only on a scanned page finds that document and page; a phrase, a
      cheque number and an account suffix are found; filters narrow by type, author, year and tag.
- [ ] The Documents ▸ PDF view shows the heat map, year range, tiles, Unrecognized and To review,
      and opens a card's PDF in the overlay at the right page, from `/box/` and from `file://`
      (Chromium tests; Safari by the maintainer).
- [ ] Setting the author of an Unrecognized document moves it to that author's folder under its new
      name, and **Update the pages** redraws it.
- [ ] Semantic search finds a document by a paraphrase the full text misses (stand-in embeddings);
      Ask answers a fixture question citing the right document and page, and refuses an answer
      with a citation it was not given.
- [ ] An author matched to a person of the box shows the document on that person's page.
- [ ] `caixa benchmark` reports the documents task for both providers.
- [ ] The naming convention document exists and its examples are tests.
- [ ] Job logs of a fixture import contain no page text.

## Risks and assumptions

- **PyMuPDF is AGPL-3.0** (decided 2026-11-24). Combined with Caixa's GPL-3.0-or-later, the
  combination carries the AGPL's terms. This matters if a box is ever offered over a network to
  others (Stage 3's presentation mode). It is stated in NOTICE.
- **OCRmyPDF's dependencies** (Tesseract, Ghostscript, their versions and languages) are installed
  by the owner; whether a given OCRmyPDF version still needs Ghostscript for plain PDF output is
  checked on the Mac. `caixa doctor` and the no-OCR path keep imports working.
- **OCR can damage a PDF** or change how it looks; validation with the unchanged-copy fallback
  means a failure costs search, never the document. The appearance tolerance is set on the fixtures
  and revisited on real scans.
- **Classifying pages** (needs OCR, broken text) by heuristics will misjudge some real PDFs; the
  thresholds are set on fixtures and adjusted on the first real folder (expect hot fixes, as in
  both earlier projects).
- **Small local models** misread documents and their context is short (Apple: about 4,000 tokens).
  Evidence checks, Caixa's own confidence rule and To review stop silent misnaming; undo and
  corrections fix what gets through. The benchmark measures accuracy, not only speed.
- **Apple's structured output and embeddings** are written from documentation and first built on
  the maintainer's Mac; the prompt-only fallback and the endpoint remain.
- **The browser's PDF viewer** inside a frame, under the box's Content-Security-Policy and from
  `file://`, differs between Chromium and Safari; checked here in Chromium and by the maintainer in
  Safari. The card's plain link always works.
- **Full-text tokenization** splits numbers like `450.00`; queries are normalized the same way, and
  the acceptance tests cover amounts and suffixes.
- **Time and space**: OCR of large scanned PDFs is slow (a resumable job, workers); archived copies
  double the space of the originals (preview shows the size, the import checks free space).
- **Phase 6 is large** and overlaps Stage 2 (the search index, the personal model). Passages are
  keyed by `item_id` so Stage 2 can extend them to mail and messages instead of starting again.
- **Sensitive content**: financial and medical documents. Everything stays local, logs carry no
  text, and the working folder is owner-only.
